Why we built Harf.

Day-to-day emails, helping clients, writing replies, then back to coding: our work moves between Arabic and English. Harf handles the keyboard-layout mistakes that come with that routine.

AAAli Alhawas/September 19, 2026/15 min read

Between clients and code

Client conversations and code share the same working day.

Between day-to-day emails, helping clients, and writing replies, we work in Arabic. Then we return to the code, comments, and technical discussions in English. That back-and-forth happens throughout the day.

The task has changed, but the active keyboard layout may still belong to the previous conversation.

So we start typing. A few words later, we look up and see hgsghl ugd;l where we meant السلام عليكم.

Fixing it means deleting the text, changing the layout, and typing the same words again. The cost is small each time, but it interrupts the work we were trying to finish.

The keys already contain the words we meant.
Could we recover them without typing again?

We built Harf around that idea: recover the intended text from the keys already pressed.

Recover the words you meant.

Harf (حرف, Arabic for “letter”) is a macOS menu-bar utility that detects text typed with the wrong Arabic or English keyboard layout.

After a pause of about a second, Harf compares what you typed with what the same keys produce in the other layout. When the evidence and safety checks allow it, it replaces the text and changes the input language for what comes next.

Follow each key through both layouts, then comparison and correction. Choose a language or pause at any step. This illustration repeats while visible; actual results depend on the text, settings, and app.

It also works in the other direction: English typed while the Arabic layout is active can be restored to English. Harf fixes the keyboard layout; spelling mistakes in the intended words may still be there.

One sequence of keys, two possible readings.

Harf starts with the keys, because a layout mistake changes their interpretation. Its pipeline keeps the recent input, compares the two readings, and checks whether a replacement is justified.

  1. Keep the keys, briefly.

    With your permission, Harf captures the keys you type. It clears the buffer when you change apps, click elsewhere, press Enter, or navigate away, so old typing does not follow you into the next conversation.

  2. Wait for a pause.

    After about a second without typing, it looks for a trailing stretch of text that might be in the wrong layout. It renders the keys under your enabled English and Arabic layouts using macOS’s own keyboard data.

  3. Compare both readings.

    Local dictionaries and letter-pattern scores help decide which reading looks like language. Harf examines words to find the candidate stretch, then considers that stretch together. It does not assume an entire bilingual message should be converted.

  4. Correct when the evidence is clear.

    A confident result can replace the wrong-layout text and switch the input source, subject to safety checks. A less certain result can appear as a suggestion. When there is not enough evidence, Harf leaves the text alone.

The comparison happens on your Mac.

Harf does not send your typing to a server or call a cloud language model. If vocabulary learning is enabled, learned words are saved locally, where you can inspect or remove them.

You do not need a plugin for each app. Harf runs at the macOS level, so it can work across native apps, browser text fields, and terminals. Apps expose text differently, though, so correction behavior can vary.

The walkthrough below follows Harf’s published source at be99434. The example scores were reproduced by building that revision. This matters: the detector’s verdict and permission to edit are separate decisions.

Keep enough context to reconstruct the text.

A macOS CGEventTap observes key-down events on a dedicated run-loop thread. Each captured event includes the physical keycode, modifier flags, keyboard type, produced text, and timestamp. The event is handed to a serial typing queue; language scoring stays out of the tap callback.

The default buffer holds 200 keys. Backspace removes the last buffered key. Enter, Tab, navigation, a click, or an app/layout change invalidate the run. There are three different clocks: a one-second pause triggers evaluation; a run the first evaluation left alone is examined once more after three seconds of stillness; ten seconds of inactivity makes the old run stale. Both the buffer size and stale interval are configurable.

Harf then replays candidate keys through macOS’s UCKeyTranslate using the enabled layouts’ keyboard tables. The alternate is tried as typed, with Shift removed, and with both Shift and Caps Lock removed. Otherwise, someone typing Arabic with Caps Lock on could produce mostly diacritics in the alternate reading. The renderer also carries dead-key composition state between keys.

The buffer describes what Harf observed, which can differ from what the editor now displays. Autocomplete can change a word without matching keystrokes. That is why the design needs a check of the text at the caret as well as a language score.

Two readings, two kinds of evidence.

The first signal is a letter bigram: how plausible each neighboring pair of letters is in that language. Harf includes word-start and word-end markers, averages the pairs’ log probabilities, and calibrates the result to a 0–1 scale. This gives unfamiliar words some credit when their spelling still resembles the language.

The second signal is dictionary coverage. It measures how much of the text is made of known words, weighted by token length: one-letter words are ignored, two-letter words weigh 0.5, and longer words weigh their length. Lookup includes normalized forms and simple English suffixes or Arabic affixes. A local user lexicon supplements the bundled lists. Normalization changes the scoring input, not the text inserted into the app.

score = 0.55 × bigram + 0.45 × dictionary

A name or technical term can be missing from a dictionary while still having familiar letter patterns. Giving those patterns slightly more weight helps the two signals complement each other. The result is a score for comparing readings; a score of 0.90 does not mean a correction has a 90% chance of being right.

In this example, the selected text has 10 letters and two words. The space completes the first word. With no text guard blocking it, the detector proposes deleting 12 characters, inserting السلام عليكم, and selecting Arabic input. The application has not changed yet.

Where does the mistake begin?

A client reply can contain Arabic prose, an English product name, and a link. Harf needs to find where the wrong-layout text begins within that mixture. Segmenter starts with a suspicious stretch at the end and checks the words to locate its boundary. The candidate ends at the caret, including any trailing separator.

But a valid dictionary word can occur by accident. One regression test types what is pr dojs through Arabic and gets صاشف هس حق يختس. The middle token, حق, is real Arabic. A strict “stop at a known word” rule would leave much of the mistaken sentence untouched.

The implementation therefore compares longer suffixes too. An extension must improve the alternate-minus-current score gap by more than 0.05. Another pass counts decisive token votes: a token needs a 0.25 gap to vote, and the alternate needs at least two votes and 70% of decisive votes. A boundary check resists crossing a plausible current-language word whose alternate letter pattern is weak.

These passes select the text to evaluate. The score thresholds, text guards, app policy, and caret checks still decide whether it can be changed. Recovering the layout also preserves an original typo such as dojs: that is what the pressed keys spell in English.

Read the implementation: Segmenter.swift · SegmenterTests.swift.

When is the evidence enough?

A higher score in the other language is only the start. The ordinary automatic path requires at least six letters, one completed word, no text guard blocking the edit, and an app policy that allows automatic correction. In the table, “current” is the active layout, “alternate” is the other layout, and “gap” is the alternate score minus the current score:

Standard automatic score gates
PresetAlternate ≥Current ≤Gap ≥
Conservative0.700.200.48
Balanced0.620.280.40
Eager0.560.340.34

There are explicit shortcuts. On that same guarded path, an alternate score of at least 0.78 with a gap of 0.50 can win despite the current-score ceiling; dictionary coverage of at least 0.80 versus at most 0.15 can also win across two or more tokens. Separately, fresh app settings enable a 0.80 confidence threshold: with at least three letters and a 0.45 gap, it may bypass the usual length/completion rules and the short-word veto. Other text vetoes still apply. On the second look, three seconds after the last key, an unfinished final word counts as finished: nobody stops that long between two letters of one word. That allowance reaches this threshold alone; the ordinary automatic path still requires a word a whitespace key actually completed.

The guards recognize patterns such as user@example.com, src/main.swift, userName, v2, and mixed Arabic/Latin letters within a token. One veto normally prevents auto-apply; two prevent even a suggestion. Under balanced settings, a suggestion still needs at least four letters, an alternate score of 0.45, and a gap of 0.18. These are deliberately different outcomes: apply, suggest, or leave alone.

Check the text before replacing it.

Before language evaluation, Harf checks whether it is paused, what the active app allows, and whether macOS Secure Input is on. It also asks Accessibility whether the focused field is secure. A confirmed secure field stops the result from proceeding. If the field type is unknown, that check alone does not stop the pipeline, so the separate Secure Input check remains important.

For an automatic edit, Harf asks the Accessibility API for text immediately before the caret and compares UTF-16 units with the exact text it intends to remove. A full match passes. The implementation also accepts a shorter matching suffix of at least four UTF-16 units, for apps that expose only part of the line. That is a deliberate compromise: it confirms the visible tail, not every character scheduled for deletion. Users can also explicitly configure apps to skip this verification.

When you accept a suggestion, Harf uses the best verification the app provides. It can continue if the app has no interface for reading the text at all. It still refuses a mismatch, an active selection, or a read that should be available but fails. An unsupported text interface and a failed read lead to different decisions.

Those reads are asynchronous. The pipeline snapshots an input serial, a counter that advances when input arrives. If it changes while verification is in flight, the pending edit is discarded. The injector checks again after waiting for held modifiers to be released: an Option-modified backspace would delete a word, not one character.

The actual edit is a sequence of marked backspace events followed by Unicode insertion, then input-source selection. Delete counts use Swift character clusters; insertion is chunked in UTF-16. The mark prevents Harf from treating its own replacement as fresh typing. The injector checks the frontmost app during deletion and insertion so an app switch can stop the sequence.

This is not an atomic editor transaction. If application focus changes halfway through, some events may already have landed; the engine reports partial progress and does not attempt a blind rollback. If the user types during a rewrite, those keys still reach the app but are excluded from Harf’s buffer. The pipeline then clears that unreliable buffer and withholds an unsafe undo. These checks reduce risk; they do not make every app behave like a native text editor.

A smart dictionary that learns your words.

Client names, product names, and technical terms are part of daily writing. Harf’s smart dictionary can learn recurring words that the bundled lists miss, then include them in future language scores. It keeps English and Arabic vocabulary separately.

The bundled dictionary is built from subtitles, so it cannot cover every team’s vocabulary. Automatic learning runs only when detection returns “ignore” with no candidate region. It records words of at least three letters that are absent from the bundled list. After ten qualifying observations, the word contributes to dictionary coverage in its language. An observation is an event recorded by the learner; ten observations do not necessarily mean ten independently written messages.

You can add a word directly without waiting for automatic learning. Manual entries can be two letters, such as pr or qa. After a manual layout flip, the card’s Learn action adds missing words from the corrected text and clears pending counts for unknown words in the original wrong-layout text. It preserves words the model already recognizes and entries you added yourself. Flipping the layout and choosing to learn are separate actions.

See and manage your dictionary.

The CLI lists learned words, manually added entries, and words still being counted. You can also add a word immediately or remove one by name:

VIEW ENGLISH VOCABULARY
harf --words list --lang en
ADD A WORD IMMEDIATELY
harf --words add webhook --lang en
REMOVE A WORD
harf --words remove webhook --lang en

Use --lang ar for Arabic vocabulary. Removing a word clears its learned count and any manual entry; future qualifying use can start learning it again.

Learned vocabulary is stored locally in ~/Library/Application Support/Harf/lexicon.json. Updates replace the file atomically, and its permissions restrict access to its owner. You can inspect or remove the saved words. Turning vocabulary learning off clears the stored lexicon.
